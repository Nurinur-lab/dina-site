Работа ведётся автономно согласно `CLAUDE.md`. Этот файл — единственный источник правды о ходе работы между сессиями.

1. **Дизайн-система** — токены, шрифты (Fira Sans Extra Condensed + Golos Text самохостинг), шапка, мобильное меню, футер, диагональная полоса, слово-«призрак», `ArchivePhoto` с типографическим фолбэком, кнопки, `/styleguide` (dev-only). Критерий: скриншоты `/styleguide` 360/768/1280 выглядят цельно.
2. **Главная** — 8 блоков по разделу 4 CLAUDE.md. Критерий: скриншоты трёх ширин просмотрены и поправлены.
3. **Внутренние страницы** — `/istoriya`, `/lyudi`, `/foto` (лайтбокс), `/klub`, `/politika`, 404.
4. **Форма обращения** — Server Action, Zod, антиспам (honeypot, тайминг, rate-limit), согласие на ПДн, Nodemailer/лог-фоллбек, e2e на успех/ошибки.
5. **SEO** — метаданные, OG через next/og, sitemap.xml, robots.txt, schema.org (SportsOrganization, Person), хлебные крошки, cookie-баннер + Метрика по условию.
6. **Качество** — axe (0 serious/critical), Lighthouse mobile (Perf≥90, A11y≥95, BP≥95, SEO=100), Core Web Vitals, финальный проход по скриншотам.
7. **Деплой и документация** — Dockerfile, docker-compose.yml (app+nginx+certbot), deploy/deploy.sh, docs/DEPLOY.md, docs/CONTENT_GUIDE.md, обновлённый README.md, актуализация docs/LAUNCH_CHECKLIST.md.

Окружение: Node v24.15.0, npm 11.12.1. Git уже инициализирован первым коммитом «Стартовый комплект» (сделан до начала этой сессии). Logo: `public/brand/logo-full.png`, 1024×1536 — подтверждён.

### Фаза 4 — Форма обращения: готово

- `src/lib/contact-schema.ts` — Zod-схема (`name`, `email`, `topic` как `z.enum` из `CONTACT_TOPICS`, `message`, `consent` как `z.literal(true)`), все сообщения об ошибках на русском.
- `src/lib/rate-limit.ts` — лимит 5 отправок в час на ключ (IP), in-memory `Map`, без внешних зависимостей (допустимо для одного инстанса — CLAUDE.md, раздел 7).
- `src/lib/mailer.ts` — `sendContactEmail` через Nodemailer; при пустом `SMTP_HOST` пишет письмо в лог сервера и просто возвращается (успех для пользователя), иначе реально отправляет через SMTP из `.env`.
- `src/app/klub/actions.ts` — Server Action `submitContactForm`: honeypot (`company`) → минимальное время заполнения 3 с (`renderedAt`) → лимит по IP (`headers().get("x-forwarded-for")`) → Zod-валидация → отправка письма. При срабатывании honeypot или тайминга — тихий «успех» (бот не узнаёт, что его поймали); при превышении лимита или ошибке SMTP — понятная ошибка на русском в `formError`.
- `src/components/klub/ContactForm.tsx` — клиентский компонент на `useActionState`: ошибки у полей (`aria-invalid`/`aria-describedby`), состояние отправки («Отправка…»), экран успеха.

**Баг, найденный и исправленный при ручном тестировании на собранном `next build && next start`:** после Server Action React 19 автоматически вызывает нативный `form.reset()` у `<form action={...}>` — ожидаемое поведение, но при ошибке валидации это стирало весь ввод пользователя. Сделал поля контролируемыми (`useState` на каждое), что сохранило текстовые поля — но `<select>` и чекбокс всё равно визуально сбрасывались: нативный `reset()` меняет их DOM-свойства (`selected`/`checked`) напрямую, а React не всегда перевыставляет控ируемое значение, если сам проп не изменился. Исправлено точечной досинхронизацией через `ref` + `useEffect` на `topic`/`consent` после каждого ответа экшена. Проверено вручную: текст, select и чекбокс теперь переживают ошибку валидации без потери данных.
- Вручную проверены все сценарии на собранном сервере: успешная отправка (письмо действительно появляется в логе сервера), ошибки валидации с сохранением введённых значений, honeypot (тихий успех, письмо НЕ попадает в лог), слишком быстрая отправка (тихий успех, без лога), лимит 5/час (6-й запрос с того же IP получает понятную ошибку).
- Новые e2e: `e2e/contact-form.spec.ts` — успех, ошибки валидации + сохранение значений, пустая форма (ошибки по каждому полю), honeypot, антиспам по времени. Тесты, которые реально расходуют лимит 5/час (успех, валидационная ошибка, пустая форма), намеренно прогоняются только на одном проекте (`desktop-1280`), а не на всех трёх вьюпортах — иначе собственные тесты исчерпали бы общий in-memory лимит друг другу (в тестовом окружении без Nginx все проекты бьют в один и тот же ключ `"unknown"`, т. к. `x-forwarded-for` не выставлен).
- `npm run check` — зелёный (36 тестов, 9 skipped по условию проекта/viewport).

## Решения, принятые без владельца

1. **`output: standalone` только по флагу `BUILD_STANDALONE`.** `next start` несовместим с `output: "standalone"` (пишет предупреждение и не поднимает сервер штатно) — нужен `node .next/standalone/server.js`. Чтобы не усложнять локальную разработку и `npm run test:e2e`/`lhci`, standalone включается только когда задана переменная окружения `BUILD_STANDALONE=1` — это выставит `Dockerfile` в фазе 7. Для обычной разработки и тестов используется обычный `next build`/`next start`.
2. **Ширины Playwright-проектов заданы вручную (360/768/1280)**, а не через готовые пресеты устройств (`devices[...]`), чтобы точно соответствовать разделу 10 CLAUDE.md, а не произвольным ширинам реальных телефонов/планшетов.
3. **`npm audit` показывает 14 уязвимостей (high) в транзитивных зависимостях `@lhci/cli`** (puppeteer-core → proxy-agent → basic-ftp/extract-zip/tmp и т. п.). Это dev-инструмент для локального запуска Lighthouse, в продакшен-сборку и на сервер не попадает. `npm audit fix --force` понижает `@lhci/cli` до `0.1.0` (breaking) — не делаю этого, фиксирую как известное ограничение дев-окружения.
4. **Golos Text подключён без явного списка `weight`.** При указании `weight: ["400","500"]` для этого шрифта Turbopack падает с ошибкой `next/font/google queries have exactly one entry` (Golos Text — вариативный шрифт с осью `wght`, и явный список статических весов конфликтует с резолвером шрифтов в Next 16.3.8/Turbopack). Решение: не передавать `weight` вовсе (используется вариативный диапазон), конкретную насыщенность задавать через CSS `font-weight: 400/500` там, где нужно.
5. **`agentRules: false` в `next.config.ts`.** По умолчанию `next dev` в Next.js 16 дописывает служебный блок "This is NOT the Next.js you know" прямо в `CLAUDE.md` при каждом запуске dev-сервера. `CLAUDE.md` — файл владельца с правилами проекта, он не должен автоматически меняться инструментом сборки. Отключил эту генерацию флагом в конфиге.
6. **Монограмма «Д» для фавикона собрана из прямоугольников (SVG-путь), а не через рендер текста системным шрифтом.** Так иконка выглядит одинаково в любой среде (macOS, Linux/Docker) независимо от того, какие шрифты установлены на машине, где собирается сайт.
7. **3 фото для блока «История коротко»** — выбраны вручную (`era-1991`, `era-dynasty`, `era-euro-1999`) как визуально разные этапы (рождение / династия 90-х / сборная-99). Не описано явно в `content/`, но не противоречит ему — просто выбор конкретных слотов из уже существующего набора.
8. **Блок «Фото-панно» использует все 8 `photos.gallery.slotIds`**, которые частично пересекаются с фото, уже показанными в «Истории коротко» (era-1991, era-dynasty). Контента для фотографий пока мало (всего 8 подготовленных слотов на весь сайт), так что пересечение неизбежно и приемлемо — это тот же принцип, что и на `/foto` в будущем. Как только появятся реальные фото и будут добавлены новые слоты, пересечение само сократится.
9. **Карточки легенд ведут на `/lyudi#<id>`** (например, `/lyudi#eremenko`) — якоря на странице `/lyudi` будут добавлены в фазе 3 (у каждой карточки легенды там будет `id={legend.id}`).
10. **Кнопка «Написать нам» в финальном блоке ведёт на `/klub#napisat`** — страница `/klub` с самой формой появится в фазе 3, а форма — в фазе 4. До этого момента ссылка технически корректна (анкор на ещё не существующую страницу), но заработает только после фазы 3/4 — это ожидаемая последовательность фаз, а не баг.
11. **`/foto` показывает все 8 `photos.gallery.slotIds` через `ArchivePhoto`, включая слоты без файла** (с типографическим фолбэком), а не только «слоты, для которых файл существует», как буквально сказано в `photos.json → gallery.note`. Это осознанное решение в пользу главного правила CLAUDE.md (раздел 5): «сайт должен выглядеть законченным без единой фотографии», которое явно сильнее частной заметки в контенте. Заметку в `photos.json` трактую как инструкцию для будущего наполнения галереи реальными фото (не добавлять id в `gallery.slotIds`, пока нет файла и его не устраивает фолбэк), а не как требование скрывать слоты в рантайме.
12. **Политика конфиденциальности (`/politika`) написана как интерфейсный/юридический текст** (не факт о клубе — правило 1 CLAUDE.md относится к фактам истории клуба, а не к обязательному по 152-ФЗ шаблону). Реквизиты оператора — плейсхолдеры с явной пометкой «ожидает подтверждения», так как `club.json → requisites` сейчас `null`; страница явно помечена как черновик, непригодный для публикации до подтверждения владельцем.
13. **У каждой карточки легенды на `/lyudi` есть `id={legend.id}`** — это и есть якоря для ссылок с карточек легенд на главной (решение 9 выше реализовано).
14. **IP для лимита отправок берётся из заголовка `x-forwarded-for`.** Next.js Server Action не даёт прямого доступа к сокету запроса, только к заголовкам. На VPS за Nginx (фаза 7) это будет работать корректно, если Nginx настроен передавать этот заголовок (`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` — учесть в `docs/DEPLOY.md`/конфиге Nginx в фазе 7). Без заголовка (как в локальной разработке без реверс-прокси) все запросы попадают в один общий ключ `"unknown"` — это сознательный fallback, не проблема в продакшен-конфигурации.
15. **Честная тишина при срабатывании антиспам-проверок (honeypot, минимальное время).** И боту, и пользователю показывается одинаковый экран «Сообщение отправлено» — это стандартная практика для ловушек: отличать бота от человека в ответе нельзя, иначе бот быстро адаптируется. Письмо в этих случаях не отправляется и не пишется в лог.
16. **Шрифт для OG-картинок — локальный TTF, скачанный один раз из `github.com/google/fonts` (OFL), а не runtime-fetch к Google Fonts.** next/og выполняется на сервере при каждом запросе OG-картинки (боты соцсетей дёргают её при каждом репосте) — завязываться на доступность `fonts.gstatic.com`/`fonts.googleapis.com` с российского VPS рискованно. next/font/google (используется для самой вёрстки) — это другое: та загрузка происходит один раз при сборке, а не на каждый запрос.
17. **`/politika` получает `robots: noindex` автоматически, пока `club.json → requisites` равен `null`.** Как только владелец подтвердит реквизиты и заполнит поле, страница на следующей сборке сама станет индексируемой — отдельного ручного шага не требуется.
18. **Баннер cookie не показывается, если `NEXT_PUBLIC_YM_ID` не задан.** Без Метрики на сайте нет необязательных (аналитических) cookie — только технически необходимые, для которых 152-ФЗ и обычная практика не требуют отдельного согласия. Как только владелец укажет `NEXT_PUBLIC_YM_ID`, баннер начнёт показываться автоматически.
19. **SportsOrganization JSON-LD размещён в `layout.tsx` (на каждой странице сайта), а не только на главной.** Это соответствует тому, как Google рекомендует размечать организацию — она описывает сам сайт/бренд, а не конкретный URL, и её наличие на каждой странице не создаёт дублей (в отличие от `BreadcrumbList`, который уникален для каждой страницы и живёт в `Breadcrumbs.tsx`).
20. **Контраст текста типографического фолбэка увеличен с 35% до 45% непрозрачности ivory.** Найдено через axe: 35% не проходило минимальный контраст 3:1 для крупного текста (WCAG AA). 45% даёт ≈3.9:1 — с запасом выше порога, и фолбэк остаётся визуально «тихим», не споря с реальным контентом, когда фото появятся.
21. **`throttlingMethod` в `lighthouserc.js` оставлен по умолчанию (`"simulate"`), не `"devtools"`.** Проверил оба варианта: при реальном троттлинге (`devtools`) результаты на этой песочнице заметно хуже и нестабильнее (Performance 0.84–0.88 с большим разбросом между прогонами) — это ожидаемо для `devtools`-режима, который требует мощной и стабильной машины и не годится для общих/виртуализированных CI-окружений (это задокументированное ограничение самого Lighthouse, не специфика проекта). `simulate` — рекомендуемый по умолчанию метод именно для таких условий.
22. **Fira Sans Extra Condensed загружается только с весом 800, вес 500 убран.** Вес 500 был заказан по дизайн-системе, но нигде в вёрстке не применялся (все места использования шрифта жёстко задают `font-weight: 800` через класс `.text-figure` или базовые стили `h1`–`h4`) — лишний файл шрифта только увеличивал LCP без видимой пользы.
23. **Brotli не включён в `docker/nginx/nginx.conf` — только gzip.** Стандартный образ `nginx:alpine` не содержит модуль `ngx_brotli`, а собирать nginx из исходников с этим модулем в рамках Dockerfile — дополнительная сложность и риск, который нельзя проверить без доступного Docker в этой среде. Gzip даёт хорошее сжатие текстовых ресурсов «из коробки» и включён полностью. Как добавить Brotli на реальном сервере (с конкретными шагами) — отдельный раздел в `docs/DEPLOY.md`.
24. **`deploy/deploy.sh` предполагает, что репозиторий уже склонирован на сервере вручную** (первый деплой описан в `docs/DEPLOY.md` отдельно). Сам скрипт — только для последующих обновлений (`git pull` + пересборка + перезапуск), это соответствует формулировке задания «сборка и перезапуск на VPS по SSH» (не первичное разворачивание).
25. **Docker недоступен в этой среде — файлы деплоя написаны и проверены статически**, без фактического `docker build`/`docker compose up`: YAML `docker-compose.yml` проверен парсером, оба shell-скрипта — `bash -n`, а рантайм-логика Dockerfile (standalone-сборка + копирование `public`/`.next/static` + запуск `server.js`) воспроизведена и проверена вручную локально (см. фазу 7 выше) — сервер поднимается и отдаёт 200 на всех проверенных маршрутах. Полную сборку образа должен проверить владелец при первом деплое по `docs/DEPLOY.md`.

## Известные особенности окружения разработки

- **В `next dev` (Turbopack) в этой песочнице не поднимается WebSocket для HMR** (`ERR_INVALID_HTTP_RESPONSE` при апгрейде). Из-за этого клиентская гидратация в dev-режиме не происходит вообще (React не подключается к серверному HTML, обработчики кликов не работают) — это артефакт среды, не баг кода. Проверено: на продакшен-сборке (`next build && next start`) гидратация и все интерактивные элементы (мобильное меню и т. д.) работают корректно. **Вывод на будущее**: любую проверку интерактивности (клики, меню, лайтбокс, форму) всегда делать через `next build && next start`, а не через `next dev`. Страницу `/styleguide` (которая в production скрыта через `notFound()`) можно смотреть только в dev — для неё визуальная (не интерактивная) проверка через dev-сервер достаточна, т.к. в стайлгайде нет интерактивных элементов, требующих гидратации.
